  (deployed as user/sofplus/addons/sofbuddy_bench_math.func), same design as
  hash_lookup/bench/sofbuddy_bench.func: 80000 flow iters/round (< 100000/frame
  budget), 10 body ops/iter, identical loop/condition/counter (`add ~i 1`) in
  every phase, adaptive to >=3 s wall (runs 1+3) or >=10 s (run 2), one round

verdict 1 (both are console commands): engine `add` (Cvar_Add: VariableValue +
atof + Cvar_SetValue) runs each increment ~1.2x faster than sofplus
`sp_sc_cvar_math_add` (Cvar_Get + struct read + atof + Cvar_SetValue). Both
are registered commands; both reach the server through Cmd_ExecuteString
whether typed at the console, queued by alias/timer/flow_while, or emitted from
a func body via Cbuf_InsertText. math_add is a slower duplicate, not a
different execution context.

verdict 2 (dispatch shape dominates; the alias trap): measured in
results_alias_overhead.txt. Two shapes:
  * func-body braced while + engine alias per iter: ~1.1x (hashmap=1) to
    ~1.4x (hashmap=0) slower for math_add; engine `add` ~1.0x.
  * while_cpu.cfg string-form flow_while (timer path): ~500 ms/iter whether
    the body is an inline string or an alias token (~1000x slower than
    func-body braced). Full 2500-iter production loop extrapolates to ~21 min.
    The trap is the cfg/timer dispatch shape, not alias expansion on top.
Inline hot loops into func bodies (already done for while_cpu/while_wait).
NOT implicated: `sp_sc_alias` / `sp_sc_func_alias` — definition handlers
(~0.3 us in spin table), not per-use expansion.

verdict 3 (storage): engine-cvar vs script-var math_add shows no gap. A
follow-up phase ran 20000 iters of DIRECT func-body lines on ENGINE cvars
(one math_add/iter, then two) in <1 s each - the same ~10 us class as M -
with exact end counts readable straight off the cvars (madd_probe/madd_i).
So math_add costs ~10 us from a func body on either storage; the alias-path
cost above is dispatch shape, not storage.

per-tick savings at ~1.7 us/op and a 100 ms tick (func-body shape):
  100 counter increments      0.17 ms   0.2 %
  1000                        1.7  ms   1.7 %
  5000                        8.3  ms   8.3 %
practical, in order of payoff:
  1. inline alias-per-iter loops (winc in while_cpu.cfg): suspected ~50-100x
     per iteration, unmeasured - see verdict 2. Direct `"add wcnt 1"` in the
     while string works too; the trap is the alias, not math_add.
  2. prefer engine `add` over `sp_sc_cvar_math_add` everywhere (~1.2x).
     Same contexts, same cvar result; math_add has no required niche.
notes:
- ratios are a LOWER BOUND: each round pays ~100 ms of 1 ms-timer latency and
  the 1 s wall clock (_sp_sc_info_time_sec) quantizes every phase.
- hashmap=0 measured (2026-09-18, restart +set _sofbuddy_hashmap 0, target 3 s):
    M  10x math_add  40000/s  (20 s/round, mvar=800000 ok)
    S  10x add       40000/s  (20 s/round, svar=800000 ok)
    T  10x add ~temp 114286/s  (7 s/round)
    S/M ratio: 1.0 (both M and S hit the same 20 s wall-clock bucket — 1 s
    clock quantizes both to 40000/s; absolutes ~2x slower than hashmap=1)
  Compare hashmap=1 validated run: M=80000 S=100000 S/M=1.25. Hashmap off
  slows both M and S on permanent script vars; T unchanged. True S/M gap at
  hashmap=0 is likely still >1 but needs a 10 s target run to resolve the
  1 s clock bucket (both landed at 20 s here).
- measurement harness: bench numbers came from server `echo` lines in sof.log
  plus rcon cvar reads (end counts). Do NOT time loops by rcon round-trip -
  UDP ack returns before the server runs the work. `sofbuddy_cmdcost_dump`
  works (PrintOut -> gi.dprintf) but its output goes to the rcon UDP reply,
  not sof.log; bench_live.py was reading the wrong sink. Tick-path prints
  like `[cpuopt] strict:` can still appear in sof.log. After map reload,
  raw Cmd_AddCommand leaves stale handlers ("already defined"); cmd_cost now
  repoints like stufftext. Run 3 with `_sofbuddy_cmdcost 1` poisoned the bench
  (S/M collapsed to 1.0); keep cmdcost off while timing.
- absolutes (~2.6x slower than the i5 host-native hashmap table) reflect this
  container's CPU under Wine; ratios travel, nanoseconds do not. Empty server;
  each round freezes the engine thread.
